# 02 · 任务判断：Jev / Laya 到底适合量化里的哪些活

## 1. 先把事实查清楚（2026-09 调研）

| | **Jev**（TypeSafe AI） | **Laya**（Convai Innovations） |
|---|---|---|
| 形态 | 闭源托管 API，`POST /v1/systemone`，目前排队申请 | Apache-2.0 开源权重，`pip install laya`，本地运行 |
| 架构 | 未公开（官方只说是"新架构 + 并行采样 + RLCD"） | ModernBERT-large（4.21 亿参数）编码器 + 决策头，非自回归，一次前向出答案 |
| 检查点 | `jev-1.13.0` / `jev-latest` | `english`（512 token）、`typed-decisions`（1024 token）、`multilingual`（mmBERT，1024 token） |
| 上下文 | 64K（Cloudflare 上是 32K） | 512–1024 token |
| 延迟（厂商口径） | 端到端 70–500 ms | T4 单问题 32.8 ms；CPU 193–464 ms |
| 价格 | 输入 $0.042 / 百万 token，输出免费 | 无调用费，成本是自己的硬件 |
| 选项上限 | 255 个 | 建议少于 20 个（多了会明显掉点） |
| 厂商承认的短板 | "零幻觉"只保证输出符合 schema，答案本身可能是错的；基准都是自己跑的 | 基座模型在 typed 任务上约 0.35（接近随机），0.766 是用 benchmark 训练集微调后的成绩；原始 logits 需要按领域重新校准 |

另外两条非常关键的用法提醒（来自 Jev 官方实践指南）：**它不是计算器**（计数、比大小不可靠），以及**状态里的内容可以影响分类**（对抗性文本需要按自己的威胁模型测试）。第二条对"读新闻"尤其重要，因为新闻是外部写的文字。

## 2. 逐条核实原来的说法

| 原说法 | 核实结果 | 判断 |
|---|---|---|
| 快速决策（毫秒级）↔ 70–500 ms | 70–500 ms 是 **Jev 走网络 API 的端到端**时间。Laya 在本机 M3 Pro GPU 上：一条短新闻、一个问题约 33 ms；一段行情描述**每个问题**约 50 ms，而且**随问题数线性增加**（E1） | "毫秒级"指的是几十到几百毫秒。分钟级、日级够用；高频（微秒级）差得很远 |
| 买/卖/持有 ↔ Choice | 格式上完全吻合 | 格式对得上不等于判断对。买卖信号好不好只能靠回测回答（E4、E5） |
| 风控判断 ↔ Noul | 格式吻合 | **硬性风控不能交给模型**。Noul 只能做"只减不增"的软否决。社区里做得最严谨的 jev-trader 也是"Jev 判断，代码执行" |
| 信号强度 ↔ Score | Score 返回连续的期望等级 | 可以用，但概率需要重新校准（E3 实测校准前后的差别） |
| 零容错（不能瞎编）↔ 零幻觉 | 厂商原话："零幻觉"只是 schema 匹配有保证，答案仍可能是错的 | **这条说法不成立。** 类型安全 ≠ 判断正确 |
| 比 LLM 便宜 400 倍 | "便宜 444.6 倍"来自厂商自己的评测（对比 GPT-5.6 Terra），媒体注明无法证明价格没有补贴 | Jev 按 token 计费确实便宜；Laya 本地运行，没有调用费 |
| 社区在做的项目 | 核实了 gist 列出的 20 多个项目（jev-trader、QuantDinger 等）；dev.to、知乎、YouTube 那几条**没有逐一核实** | 共同的设计模式是：模型只负责判断，执行和风控留在代码里 |

## 3. 量化任务适配矩阵

判断标准只有一条：**这件事如果能写成一行 `if`，就不要问模型；只有需要综合多条线索，或者输入本身是文字时，模型才可能有增量。**

| 任务 | 适合度 | 理由 | 本项目怎么验证 |
|---|---|---|---|
| 因子计算、回测、定价、协整 | ✗ | 这是数学，代码又快又准 | 不做 |
| 单个数值阈值（RSI>70、价格>均线） | ✗ | 一行 `if` 就是 100% 正确；模型"不是计算器" | **E2**：原始数字、数字写成句子、数字加文字描述，三种给法对比 |
| 综合多条技术线索判断市场状态 | △ | 规则也能写，但阈值和组合方式都很主观，模型有可能更"模糊地"综合 | **E4-A**（合成市场，有真值）、**E5**（真实 ETF） |
| 策略路由（趋势、均值回归、空仓） | △ | 本质上是上一条的下游 | **E4-B** |
| 风控否决 | △ | 只能是软否决，只减不增；硬约束写在代码里 | **E4-D**、**E5** |
| 新闻 / 公告 / 研报情绪 | ✓ | 输入就是文字，规则很难写全（否定句、隐含意思、行话），这正是它的主场 | **E3**（真实标注推文）、**E4-C**（合成市场里的新闻交易） |
| 高频交易 | ✗ | 延迟差了 3–4 个数量级 | **E1** |

## 4. 实验前写下的假设

这些在跑 E3–E5 之前写好，结果见 [04-实验报告](04-实验报告.md)，不管结果好坏都如实报告。

- **H1（E1）** Laya 在本机能做到几十毫秒一问，但单条状态的问题越多，延迟越接近线性增长（不像厂商说的"多问几个几乎不增加延迟"）。
- **H2（E2）** 直接给原始数字，Laya 答不好阈值题；先把数字转成文字再问，才答得好。
- **H3（E3）** 零样本 Laya 读新闻明显好于关键词词典，但**不如**用 9,500 条标注数据训练的 TF-IDF。把 Laya 没把握的少数样本交给 Claude，能用很小的成本补上一截。
- **H4（E4）** 在已知真值的合成市场里，Laya 读到的 regime 未必比手写规则准；新闻交易捕获的 alpha 大致按"读新闻的准确率"排序。
- **H5（E5）** 在只有技术指标的真实市场里，Laya 的信号相对规则基线没有显著增量。

## 5. 和 Claude 怎么结合

两者不是替代关系，而是**快思考和慢思考**的分工：

| | Laya（System 1） | Claude（System 2） |
|---|---|---|
| 擅长 | 大批量、固定格式、要概率的判断 | 读长文、推理、处理没见过的情况、写结论、设计问题 |
| 成本 / 延迟 | 本地，几十毫秒，没有调用费 | 每次请求几秒，按 token 计费 |
| 失败方式 | 自信地答错（尤其是数字、长尾说法） | 慢、贵；每次调用都要花钱 |

三种结合方式都实现了：

1. **级联**（`CascadeEngine`）：Laya 答全部样本，确定度低的那部分批量交给 Claude，而且用**同一套类型化问题和 JSON schema**。E3 给出"升级比例 → 准确率 → 成本"曲线。
2. **Laya 作为 Claude 的工具**（MCP server + Claude Code skill）：Claude 在对话里调用 `screen_headlines` 一次筛几百条，只精读 `needs_review` 的那几条。这就是"让 Laya 成为 Claude 的一部分"最直接的做法，不需要改动 Claude 本身。
3. **Claude 当老师**：Claude 负责设计题目，它给出的标签也可以拿来校准或蒸馏 Laya。当前实现的是校准；蒸馏（微调）列在后续工作里。
